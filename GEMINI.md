# Path of Building - Project Instructions

These instructions are foundational mandates for working on this Path of Building fork.

## Project Overview

Path of Building Community is an offline build planner for Path of Exile, written in Lua (LuaJIT 5.1). It runs on a custom 2D graphics host (SimpleGraphic) and provides comprehensive offense/defense calculations, passive tree planning, item/gem configuration, and build sharing.

This fork specifically adds a **LÖVE 2D frontend** for cross-platform support (especially Linux) and maintains its own release lifecycle while rebasing on top of the official upstream repository.

---

## Upstream Syncing & Rebase Workflow

This project tracks **`upstream/master`** (stable releases) and applies the LÖVE port changes on top.

### Automated Sync
Always use the custom sync script to minimize manual conflict resolution for auto-generated or noisy files:
```bash
./love/scripts/sync-upstream.sh
```
This script automates the rebase and handles specialized merge logic for `manifest.xml` and `ModCache.lua`.

### Merge Strategies
The `.gitattributes` file is configured to automatically resolve conflicts in several auto-generated files (ModCache, Gems, Uniques) by preferring the "ours" version (which is the upstream version during a rebase).

### Rebase Procedure
1.  **Squash fixup commits**: `git rebase -i upstream/master`
2.  **Rebase**: `git fetch upstream && ./love/scripts/sync-upstream.sh`
3.  **Verify**: Check `LOVE_VERSION_TAG` in `love/shim/init.lua` and ensure `manifest.xml` includes both official and custom sources.

## Development Setup

### Running the Application
-   **Via LÖVE** (Cross-platform, recommended):
    ```bash
    cd love && love .
    ```
    Requires LÖVE 11.5+. The shim layer in `love/shim/` bridges LÖVE to SimpleGraphic's API.
-   **Via SimpleGraphic** (Windows only):
    ```
    ./runtime/Path of Building.exe
    ```

### Dev Mode
Enabled automatically on the `dev` branch or when running from source.
-   `F5`: Restart in-place.
-   `Ctrl` + `~`: Toggle console.
-   `Alt` (Hold): Show debug tooltips and internal modifiers.
-   `Ctrl` + `F5`: Regenerate `ModCache.lua`.
-   Updates are disabled in Dev Mode.

-   **System Tests**: `spec/System/`
-   **Build Regression Tests**: `spec/TestBuilds/`

### Running Tests

```bash
docker-compose up

# Directly with Docker
docker run ghcr.io/pathofbuildingcommunity/pathofbuilding-tests:latest busted --lua=luajit
```
Configuration is in `.busted`. Tests tagged `builds` are excluded by default.

## Code Style & Architecture

### Standards
-   **Indentation**: Tabs (not spaces).
-   **Line length**: 120 characters max.
-   **Lua version**: LuaJIT 5.1.
-   **File naming**: PascalCase (e.g., `CalcOffence.lua`).
-   **Functions/Variables**: camelCase (e.g., `AddMod()`).

### Class System
Custom OOP via `newClass()` in `src/Modules/Common.lua`. All UI controls inherit from `Control`. Properties support lazy evaluation via `GetProperty()`.

### Core Pipeline
1.  **CalcSetup.lua**: Builds modifier databases.
2.  **CalcOffence.lua** / **CalcDefence.lua**: Main calculation modules.
3.  **ModParser.lua**: Parses game text into `ModCache.lua`.
4.  **Launch.lua**: Bootstrap and renderer initialization.

## Key Development Rules

### Spell Checking (cspell)
-   A pre-push hook runs **cspell** on changed files.
-   **Centralized Dictionary**: Add new technical terms or project-specific words to `.cspell.json` at the root.
-   Avoid file-level `cspell:words` directives when possible; use the root config instead.
-   Use `cspell:ignore` for upstream code with typos to avoid modifying those lines.

### Repository Maintenance
-   **Auto-Generated Files**: Do not edit files in `src/Data/` with the "automatically generated" header. Edit scripts in `src/Export/Scripts/` and rerun the exporter instead.
-   **ModCache**: If mod parsing logic changes, you MUST regenerate and commit `src/Data/ModCache.lua`.
-   **manifest.xml**: Do not auto-commit on push. It is regenerated by `love/scripts/generate-manifest.sh` during release builds.

## Release Workflow (LÖVE)

1.  CI (`.github/workflows/love-build.yml`) triggers on `love-v*` tags.
2.  CI injects the tag into `LOVE_VERSION_TAG` and runs `generate-manifest.sh`.
3.  To release: `git tag love-v0.X.Y && git push origin love-v0.X.Y`.
